Status model — stored vs effective

Stored Membership.Status: active · expired · frozen · cancelled · pending.

MembershipOperational.GetEffectiveStatus() computes the date-aware status on the Cairo calendar: adds scheduled (future start), derives expired from EndDate, frozen-with-expiry → expired.

A Hangfire job (MembershipStatusExpiryJob) syncs stored status; front-desk decisions use the computed one.

CRITICAL RULE — Never trust stored Membership.Status alone. Effective status is date-aware and Cairo-calendar computed (GMS.Core/Utilities/MembershipOperational.cs). Cash assign/renew ⇒ active; non-cash ⇒ pending.

08 Authentication Architecture

Three user representations — verified chain

ApplicationUserAspNetUsers · JWT sub = its Id
→ AppUser.UserId stores that Identity ID as string
AppUserdomain staff record · separate NEWSEQUENTIALID PK
→ GymMember.AppUserId FK (nullable)
GymMembermember profile · encrypted NationalID
CRITICAL — JWT sub ≠ AppUser.Id. JWT sub = ApplicationUser.Id. Comparing against the wrong PK is a documented past-mistake class (see CheckinService comments).

Staff login IMPLEMENTED

gym_code + email + password → tenant match → tenant match on user → password check → JWT + refresh token. Refresh hashes stored, revocation supported.

Member OTP IMPLEMENTED

Phone → 6-digit OTP (Otp.NET, 5-min TTL cache, pluggable delivery strategy incl. MockOtpSender) → member JWT with role Member.

Activation code IMPLEMENTED

Staff issues code; peppered hash stored (MemberAppActivationCode), 24 h expiry, one-time consume, RowVersion-guarded.

JWT claims (TokenService)

sub · email · jti · tenant_id · gym_code · first_name/last_name · role claims · one discrete perm claim per permission (chosen over bitmask for debuggability).

On first member login the backend lazily creates ApplicationUser + AppUser and links GymMember (FindOrCreateMemberIdentityUserAsync).

17 ⛔ DO NOT BREAK THESE CRITICAL RULES

1 · Attendance validation order CRITICAL RULE

The 8-step gauntlet (tenant → member → membership → freeze → time → sessions → write → atomic decrement) must stay in exact order.

2 · Effective membership status CRITICAL RULE

Never trust stored Membership.Status alone — use MembershipOperational.GetEffectiveStatus (Cairo-day aware).

3 · Inventory truth CRITICAL RULE

StockMovement ledger is the source of truth; StockBalance is a cache written only via IStockLedgerService (RowVersion-guarded).

4 · Cash drawer invariant CRITICAL RULE

Cash sale or cash membership assign/renew ⇒ PaymentTransaction + shift CashMovement sharing the ShiftId.

5 · Combined query filters CRITICAL RULE

Tenant + soft-delete must remain ONE HasQueryFilter call per type — a second call silently replaces the first (historical bug).

6 · Identity relationship CRITICAL RULE

JWT sub = ApplicationUser.Id ≠ AppUser.Id; link is AppUser.UserId (string) then GymMember.AppUserId.

7 · Idempotency HIGH

SaleIdempotencyKey + reference-idempotent ledger posts prevent duplicate financial/stock effects on retries.

8 · Referral reward hold HIGH

Rewards grant only after ProcessReferralRewardHoldsJob — never instantly at conversion.

9 · Suspension grace buffer HIGH

Suspended tenants may check-in only during the 72-hour buffer window; everything else returns 402.
