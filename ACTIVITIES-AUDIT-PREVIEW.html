1 · Current Implementation Status (from code)

✅ Implemented correctly

  • Core model is independent: Activity ≠ Plan (separate entities linked only via PlanEntitlement). Facility is an Activity kind (class | facility) with system Gym Floor bootstrap.
  • Entitlement modes: included / unlimited / limited(+QuotaLimit+QuotaPeriod) on PlanEntitlement.
  • Schedule entity with DaysOfWeek JSON, times, capacity, coach, effective window.
  • Booking lifecycle fields: booked → cancelled / checked_in, source, covering membership, Sale link, attendance link.
  • Drop-in price field exists on Activity (DropInPrice).
  • Duplicate-booking guard and capacity count in CreateBookingAsync.
  • Tenant isolation via global query filters + explicit TenantId predicates.
  • Admin Classes page exists (classes-app.js talks to activity endpoints).

❌ Missing / broken (confirmed)

  • No session generation from schedules — nothing anywhere creates ActivitySession rows from a recurring schedule. Schedules are stored but never materialize into bookable sessions. P0
  • No quota enforcement — CreateBookingAsync ignores QuotaLimit/QuotaPeriod entirely. Scenario A "8/month" is not enforced. P0
  • Capacity race: load-then-count check, no transaction/unique constraint — two concurrent books can exceed capacity. P0
  • No member-facing API — all booking/session endpoints require staff permissions; Member App cannot list or book sessions. P1
  • Drop-in payment not wired — DropInPrice/SaleId never used in the booking flow. P1
  • No no-show status; cancel doesn't distinguish quota refund rules. P1
  • No facilities-specific UX; facility vs class rendered the same. P2

5 · Booking Flow (proposed backend sequence)

POST /api/member/activity-sessions/{id}/book  (member JWT)
  1. resolve member from JWT → tenant match
  2. load session + activity (must be active, future, visible)
  3. entitlement check: covering membership today → PlanEntitlement for this activity
      • none + activity.DropInPrice → require paid drop-in sale first (reuse POS)
  4. capacity: atomic INSERT guarded by unique index (sessionId, memberId, activeStatus)
      + transactional count check inside the same tx → race-safe
  5. quota: if mode=limited → count member's consumed bookings in period → reject if exhausted
  6. return BookingDto incl. remaining quota for confirmation screen

7 · Product Decisions Needed From You

Q1 — Cancellation & quota:

If a member cancels a booked session, does the monthly quota get refunded? Options: (a) yes always, (b) only if cancelled ≥ X hours before start, (c) never.

Q2 — Late-cancel window:

Should cancelling within e.g. 2 hours of start mark "late cancel" (consumes quota / possible fee)?

Q3 — No-shows:

Auto-mark booked members as no-show after session end? Any penalty?

Q4 — Drop-in expiry:

Does a purchased drop-in apply to one specific session only, or stay valid N days?
