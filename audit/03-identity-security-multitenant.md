### 1.4 Password policy

- **Per-tenant overlay**: `RolePermissionResolver.ParseOverlay`/`Resolve` (`RolePermissionResolver.cs:55-115`) lets a tenant customize the `Manager`/`Receptionist`/`Trainer` permission sets (the `EditableRoles`, line 16) via a `role_permissions` JSON blob stored in `Tenant.Settings` (key from `TenantSettingsKeys.RolePermissions`). **`Owner` is explicitly hard-locked and cannot be downgraded** (`Resolve`, lines 102-106, always uses the default provider for Owner regardless of overlay) — a sound design choice preventing an owner from accidentally/maliciously locking themselves out or a compromised settings row from stripping Owner privileges.

- **Authorization enforcement mechanism**: pure claims check, no DB/Redis call per request — `PermissionAuthorizationHandler.HandleRequirementAsync` (`D:\GMS\GMS\GMS.Api\Authorization\PermissionAuthorizationHandler.cs:13-23`) does `context.User.HasClaim(Permissions.ClaimType, requirement.Permission)`. Dynamic policies (`"Permission:checkin.manual"` etc.) are created on-demand by `PermissionPolicyProvider` (`D:\GMS\GMS\GMS.Api\Authorization\PermissionPolicyProvider.cs`) rather than requiring one `AddPolicy` call per permission (`Program.cs:246-251` comment confirms this design).

### 2.3 Authorization policies and enforcement consistency
- Static role policies defined centrally in `Program.cs:219-244`: `OwnerOnly`, `ManagerOrAbove`, `AnyStaff`, `AuthenticatedMember`, `AuthenticatedEmployee`, `AnyAuthenticated`, plus three Platform-plane policies (`PlatformSupportOrAbove`, `PlatformOpsOrAbove`, `PlatformAdminOnly`) that **explicitly pin `AddAuthenticationSchemes(PlatformAuthConstants.AuthenticationScheme)`** (lines 231, 236, 241) so a tenant-audience JWT can never satisfy a platform policy even if it somehow carried a matching role claim — a deliberate, well-designed cross-plane guard.

- **Enforcement is applied at the controller class level** in the overwhelming majority of controllers (58 of 60 controllers have at least one `[Authorize]` occurrence — see raw counts gathered during this audit), which is good baseline coverage, but the counts alone don't prove every *action* has the *right* permission — a line-by-line audit of all 60 controllers' individual actions was out of scope for this pass; spot-checked controllers (`AuthController`, `PaymentsController`, `HealthController`) below.

### 3.1 Tenant resolution per request
`TenantMiddleware` (`D:\GMS\GMS\GMS.Api\Middleware\TenantMiddleware.cs:16-155`), registered in the pipeline **after** `UseAuthentication()` and **before** `UseAuthorization()` (`Program.cs:322-325`, comment: "Authentication → TenantMiddleware → Authorization (ORDER IS CRITICAL)"):

### 3.2 Isolation enforcement: centralized (EF Core global query filters) — confirmed
This codebase uses **centralized enforcement**, not scattered manual `.Where(x => x.TenantId == ...)` calls, as the primary mechanism:
- `GymFlowProDbContext.ApplyGlobalQueryFilters` (`D:\GMS\GMS\GMS.Infrastructure\Persistence\GymFlowProDbContext.cs:192-399`) applies a combined `HasQueryFilter(x => x.TenantId == _tenantContext.TenantId && !x.IsDeleted)` predicate to **~60 entity types** (full list at lines 39-60, `TenantScopedEntityTypes`, and the actual `HasQueryFilter` calls at lines 202-399) — covering members, memberships, sales, invoices, shifts, refunds, inventory (products/warehouses/stock/purchasing), HR (employees/payroll/leave/attendance), activities/bookings, notifications, audit events, refresh tokens, etc.
- The filter binds to `ITenantContext` (`D:\GMS\GMS\GMS.Infrastructure\Services\TenantContext.cs`), a **scoped** DI service (`InfrastructureServiceExtensions.cs:132`, `AddScoped<ITenantContext, TenantContext>`) whose `TenantId` defaults to `Guid.Empty` until `TenantMiddleware.SetTenant(...)` populates it per-request. Because EF Core query filters that reference a `DbContext` instance field are re-evaluated per-`DbContext`-instance at query-translation time (a documented EF Core pattern, not unique to this codebase), each request's queries are correctly scoped to that request's resolved tenant, despite the compiled model itself being built/cached once per `DbContext` type. If `TenantId` is ever `Guid.Empty` (tenant not yet resolved), the filter becomes `TenantId == Guid.Empty`, which **fails closed** (returns nothing) rather than leaking all tenants' rows.
- Soft-delete filter (`ApplySoftDeleteFilter`, lines 417-432) is applied separately only to entity types **not** already in `TenantScopedEntityTypes`, specifically because "EF Core does not merge multiple `HasQueryFilter` calls on the same entity; a second call replaces the first outright" (doc-comment, lines 34-38) — the code explicitly guards against a real historical bug class here, which is a good sign of engineering maturity around this exact risk.
- **Deliberate, documented escape hatches** (`IgnoreQueryFilters()`) are used in specific, justified places — chiefly:
  - Pre-authentication tenant/user resolution in `AuthService.cs` (tenant lookup by gym code, refresh-token lookup by hash, member/employee lookup during OTP/activation — no ambient tenant context exists yet by definition), e.g. `AuthService.cs:100, 165, 201, 221, 292, 303, 345, 357, 397, 447, 547, 636, 722, 798, 825, 831`.
  - Background/Hangfire job contexts, which have **no ambient `ITenantContext`** since they run outside an HTTP request scope. This is explicitly called out in code comments: `InvoiceService.cs:87-88` — *"Hangfire job scope has no ambient ITenantContext — IgnoreQueryFilters throughout and resolve/filter by TenantId explicitly instead"* and again at `InvoiceService.cs:268-269`. In these cases the code **does** manually re-add an explicit `.Where(...TenantId == tenantId...)` or looks up by a primary key that was itself only reachable via a tenant-scoped path (e.g. `InvoiceService.cs:124`, `.FirstOrDefaultAsync(t => t.Id == tenantId)`).
  - Numeric-sequence allocators (`AllocateStaffNumberAsync`, `AllocateEmployeeNumberAsync`, `AllocateContractNumberAsync` in `AdminService.cs:663-676` / `EmployeeService.cs:377, 387`) that need to see soft-deleted/cross-filter rows to avoid number collisions — these all take an explicit `tenantId` parameter and re-filter by it (confirmed pattern, not verified line-by-line for every one of the ~30+ occurrences found).
- **Verdict**: the primary, dominant pattern is centralized (global query filter). Manual re-filtering only appears as a deliberate, commented compensating control in the specific contexts (pre-auth, background jobs, deliberate cross-tenant admin lookups) where the central filter cannot apply. This is a **materially better architecture** than "isolation enforced by convention in every LINQ query," and is a strong positive finding for the codebase's tenant-safety posture.

### 3.3 Background jobs / Hangfire — tenant scoping check
- `AnalyticsAggregationJob.ExecuteAsync` (`D:\GMS\GMS\GMS.Infrastructure\Jobs\AnalyticsAggregationJob.cs:28-107`) is the clearest example: it explicitly loops **`foreach (var tenant in tenantIds)`** (line 50) and runs one parameterized `ExecuteSqlInterpolatedAsync` MERGE per tenant, with every subquery inside the SQL scoped by `TenantId = {tenant.Id}` (lines 61-69, all via safe FormattableString interpolation → EF Core parameterizes these, **not string concatenation** — see §4 SQL injection check). A per-tenant `try/catch` (lines 52, 97-100) also means one tenant's aggregation failure doesn't abort others' — good isolation of failure blast-radius too.
- `MembershipExpiryNotificationsJob.ExecuteAsync` (`D:\GMS\GMS\GMS.Infrastructure\Jobs\MembershipExpiryNotificationsJob.cs:29-74`) queries **across all tenants** with `IgnoreQueryFilters()` (line 49) — by design, since it's a global cron sweep — but **carries `TenantId` through in the projection** (line 51, `.Select(m => new { m.Id, m.MemberId, m.EndDate, m.TenantId })`) even though the enqueued child job (`svc.SendExpiryReminderAsync(membership.MemberId, daysLeft)`, line 64-65) only passes `MemberId`, not `TenantId`. Since `MemberId` (a GUID) is unique per row regardless of tenant, this is **not currently exploitable as a cross-tenant leak**, but it does mean the downstream `IWhatsAppService.SendExpiryReminderAsync` implementation must itself re-resolve the member's tenant safely (not verified in this pass — UNKNOWN — REQUIRES VERIFICATION, check that implementation doesn't need a tenant context to look the member up and doesn't accidentally pick up a same-ID row from a different tenant, which is only possible if GUIDs could collide, which they can't in practice).
- No Hangfire job was found that iterates tenant data **without** either (a) an explicit per-tenant loop with parameterized TenantId, or (b) carrying TenantId through to any onward tenant-scoped write. **No cross-tenant job-processing bug was identified**, though full coverage of all 11 Infrastructure jobs + 14 Application jobs was not exhaustively line-read (spot-checked 2 of the highest-risk-looking ones: the raw-SQL aggregation job and a member-selecting notification job).

### 3.4 File storage and reports
- Upload storage is a static `wwwroot/uploads` folder (`D:\GMS\GMS\GMS.Api\wwwroot\uploads`) served via `app.UseStaticFiles()` (`ProductionHostingExtensions.cs:117`). **UNKNOWN — REQUIRES VERIFICATION**: this pass did not trace the upload-handling controller(s) (likely `HrEmployeeDocumentsController`, `ImportsController`, or member-photo upload in `MembersController`) to confirm whether uploaded file paths/blob keys are namespaced by `TenantId` (e.g. `uploads/{tenantId}/{file}`) and whether `UseStaticFiles()` middleware — which serves files with **no authentication or authorization check at all** by default in ASP.NET Core — could allow an authenticated user of Tenant A to fetch Tenant B's uploaded file simply by guessing/enumerating its static URL. **This is a plausible cross-tenant leak vector that should be verified before offline/on-prem packaging**, since static file serving bypasses the entire JWT+TenantMiddleware+EF-query-filter stack described above — none of those protections apply to a `GET /uploads/...` static file request. Flagged in §4 as a risk to verify.
- Reports (`ReportsController.cs`, `InventoryReportsController.cs`) go through the normal controller → service → `GymFlowProDbContext` path, so they inherit the same global query filter protection as everything else in §3.2 — no separate reporting-specific tenant-bypass mechanism was found.

### 3.5 Explicit search for missing-tenant-filter queries
Actively searched `GMS.Application/Services` for `IgnoreQueryFilters()` calls (56 occurrences found across the codebase) to find any that omit an explicit tenant re-filter where **peer code in the same class/pattern does include one**. One concrete finding:

- **`ImportService.RollbackAsync`, `D:\GMS\GMS\GMS.Application\Services\ImportService.cs:265-267, 278-279, 284`**:
  ```csharp
  var hasActivity = await _dbContext.GymAttendances.IgnoreQueryFilters().AnyAsync(a => a.MemberId == memberId)
      || await _dbContext.Sales.IgnoreQueryFilters().AnyAsync(s => s.MemberId == memberId)
      || await _dbContext.PaymentTransactions.AnyAsync(p => p.MemberId == memberId);
  ...
  var membership = await _dbContext.Memberships.IgnoreQueryFilters()
      .FirstOrDefaultAsync(m => m.Id == membershipId.Value);
  ...
  var member = await _dbContext.GymMembers.IgnoreQueryFilters().FirstOrDefaultAsync(m => m.Id == memberId);
  ```
  These four queries filter **only by `MemberId`/`Id`, with no `TenantId` predicate**, unlike the immediately preceding query in the same method (`ImportService.cs:253-255`, `.Where(r => r.BatchId == batchId && r.TenantId == tenantId && ...)`) and unlike `ImportService.ValidateAsync`/`ExecuteAsync` in the same file (lines 402, 426-428, which **do** re-add `.Where(p => p.TenantId == tenantId ...)` after `IgnoreQueryFilters()`).
  - **Exploitability**: `memberId`/`membershipId` here are sourced from `row.CreatedMemberId`/`row.CreatedMembershipId`, and `row` was already filtered to `r.TenantId == tenantId` at line 254 — so in the **current call path**, `memberId` cannot actually belong to another tenant, and this is **not presently exploitable as a cross-tenant leak**. However, it is an inconsistency with the codebase's own stated defensive pattern ("IgnoreQueryFilters... resolve/filter by TenantId explicitly instead") and is exactly the kind of code that becomes a real vulnerability the moment it's copy-pasted into a new method that doesn't have that upstream guarantee, or if `CreatedMemberId` could ever be attacker-influenced. **Flag as P2 (defense-in-depth gap, not a currently-live leak).**
- No other query was found where a **sibling/peer query in the same file** demonstrated the tenant-filtered pattern while the flagged one omitted it — the rest of the 56 `IgnoreQueryFilters()` occurrences reviewed either (a) run pre-authentication with no tenant to filter by yet, (b) immediately re-add an explicit `TenantId` predicate, or (c) resolve by a token hash / activation-code hash that is unique across the whole system by construction (so a tenant filter would be redundant, not missing).

## 4. Ranked Security Risk List

### P0 — Critical
**None found.** No hardcoded secrets, no unauthenticated auth-bypass, no confirmed cross-tenant data leak, and no SQL-injection vector were identified in this pass. This is a notably mature codebase for these specific classes of risk — see caveats under P1/P2 for things that need live verification before that conclusion can be fully trusted.

### P1 — High
1. **No rate limiting on `POST /api/auth/login`.**
   - File: `D:\GMS\GMS\GMS.Api\Controllers\AuthController.cs:26-56`.
   - Why it matters: staff/owner password login is protected only by per-account Identity lockout (5 failed attempts / 5-minute lockout, `InfrastructureServiceExtensions.cs:71-72`). An attacker can spray login attempts across many different `(GymCode, Email)` pairs from a single IP with zero throttling, since each individual account's lockout counter is independent and no IP/global limiter policy (`checkin-policy`, `member-activate-policy`, `employee-activate-policy` — none of which target `/api/auth/login`) applies here.
   - How to verify without exploiting: inspect `AuthController.Login` for an `[EnableRateLimiting(...)]` attribute (there is none) and confirm no global rate-limiter middleware config in `Program.cs` applies by default to unattributed endpoints (`app.UseRateLimiter()` at `Program.cs:320` only activates configured/attributed policies, it doesn't add an implicit global limit).

2. **CORS falls back to reflecting any origin in Production when `Cors:AllowedOrigins` is empty.**
   - File: `D:\GMS\GMS\GMS.Api\Extensions\ProductionHostingExtensions.cs:53-58` — `else if (env.IsProduction()) { policy.SetIsOriginAllowed(_ => true)... }`.
   - Confirmed live in shipped config: `D:\GMS\GMS\GMS.Api\appsettings.Production.json:25-27` sets `"Cors": { "AllowedOrigins": [] }` — i.e., **as currently configured, Production runs with `SetIsOriginAllowed(_ => true)`**, which is functionally equivalent to `AllowAnyOrigin()` (reflects the request's `Origin` header back) combined with `AllowAnyMethod().AllowAnyHeader()`.
   - Why it matters: this policy does not call `.AllowCredentials()` (not seen in the reviewed code), which limits the practical exploitability for cookie/credentialed-session attacks (browsers block credentialed cross-origin responses without a matching `Access-Control-Allow-Credentials`), and since auth uses Bearer tokens in headers (not cookies) rather than ambient browser credentials, the classic CSRF-via-CORS risk is reduced — but it still means **any website can make cross-origin XHR/fetch calls to the API and read the JSON response** if it can otherwise obtain/attach a valid bearer token (e.g. via an XSS on a trusted frontend origin, or a malicious browser extension), and it removes CORS as a defense-in-depth layer entirely in Production until `Cors:AllowedOrigins` is populated with the real frontend origin(s).
   - How to verify: confirm the live Production `appsettings.Production.json` deployed to MonsterASP still has an empty `Cors:AllowedOrigins` array (or check the env var override) — if so, this permissive fallback is active today, not just a theoretical dev fallback.

### P2 — Medium
1. **Weak password policy**: `RequiredLength = 6`, `RequireNonAlphanumeric = false` — `D:\GMS\GMS\GMS.Infrastructure\InfrastructureServiceExtensions.cs:65-69`. A 6-character password satisfying digit+upper+lower (e.g. `Passw1`) is accepted. Verify by attempting to register/reset a staff password with a 6-character value in a test environment.

2. **`ImportService.RollbackAsync` omits the tenant re-filter its sibling methods use** after `IgnoreQueryFilters()` — `D:\GMS\GMS\GMS.Application\Services\ImportService.cs:265-267, 278-279, 284` (detailed in §3.5). Not currently exploitable (upstream `memberId` is already tenant-guaranteed), but inconsistent with the codebase's own defensive pattern and a latent risk if the method is ever refactored or reused. Verify by code review / unit test asserting the method rejects a `memberId` belonging to a different tenant than `tenantId`.

3. **Uploaded file storage may not enforce tenant isolation at the static-file layer** — `wwwroot/uploads`, served via `app.UseStaticFiles()` (`D:\GMS\GMS\GMS.Api\Extensions\ProductionHostingExtensions.cs:117`). Static files bypass the JWT/TenantMiddleware/EF-query-filter stack entirely. **Not confirmed as a live leak in this pass** (the upload-path-generation code was not traced) but flagged because it's structurally the one place in the app where the otherwise-strong centralized tenant-isolation model (§3.2) plainly does not apply. Verify by finding the controller(s) that accept file uploads (likely HR documents, member photos, import files) and checking whether the resulting URL/path includes `TenantId` and, more importantly, whether it's *guessable/enumerable* and whether an authenticated Tenant-B user (or even an anonymous user, since static files need no `[Authorize]`) can fetch a Tenant-A file by URL.

4. **Refresh-token-reuse detection does not revoke the whole token family.** `AuthService.RefreshTokenAsync`, `D:\GMS\GMS\GMS.Application\Services\AuthService.cs:205-213` — a reused/stale token is rejected and logged, but its descendant chain (tokens issued after it was rotated) is not proactively revoked, so if an attacker captured an old refresh token and the legitimate user already rotated past it, the attacker's *specific* stale token is blocked, but this doesn't itself invalidate the current active session it was replaced by (which is arguably correct if the "attacker" signal is a false positive from clock/retry issues, but is a weaker posture than full family revocation on reuse-detection, which is the OWASP-recommended pattern for refresh token theft).

5. **OTP delivery is SMTP/email-only and requires outbound internet** — `D:\GMS\GMS\GMS.Application\Services\EmailOtpDeliveryStrategy.cs` (whole file), config at `D:\GMS\GMS\GMS.Api\appsettings.json:98-108`. Directly relevant to the offline "Local Lifetime Edition": member OTP sign-in as currently built cannot function without internet+working SMTP credentials. The staff-issued activation-code flow (`member-activate`/`employee-activate`) is internet-independent and should be the basis for member/employee login in an offline build. This is a **design/feasibility finding**, not a vulnerability.

### P3 — Low
1. **Baked-in permission claims lag live permission changes** until the user's access token is refreshed — `D:\GMS\GMS\GMS.Application\Services\AuthService.cs:69-94`, `D:\GMS\GMS\GMS.Infrastructure\Services\TokenService.cs:60-66`. A revoked permission (or demoted role) remains effective for up to the access-token lifetime (15 min prod / 60 min dev) and potentially longer if the refresh flow keeps re-minting tokens before the affected user's session is separately terminated. Verify by changing a test user's role/tenant permission overlay and confirming their *already-issued* token still carries the old `perm` claims until expiry.

2. **Rate-limiter partition key not confirmed** for `checkin-policy`/`member-activate-policy`/`employee-activate-policy` — `D:\GMS\GMS\GMS.Api\Program.cs:94-118`. Comments say "per IP" but the actual partitioning wiring (`RateLimitPartition.GetFixedWindowLimiter(...)` with a per-IP key selector) was not located in the reviewed slice of `Program.cs`; if these are actually global (unpartitioned) fixed windows, one abusive client could exhaust the shared quota for all legitimate clients. Verify by reading the full `AddFixedWindowLimiter` lambda bodies for a partition-key selector, or by load-testing from two different IPs against the same policy.

3. **No global authorization fallback policy** (`Program.cs`, no `options.FallbackPolicy` found) — means any newly-added controller/action that forgets `[Authorize]` is anonymous by default. No current instance of this was found (§2.4), but it's a structural gap worth closing (`options.FallbackPolicy = new AuthorizationPolicyBuilder().RequireAuthenticatedUser().Build();` with explicit `[AllowAnonymous]` on the few endpoints that need it) especially before this codebase is forked/maintained for a new offline edition by a potentially different team.

4. **No SQL injection vectors found** — every raw-SQL call site uses `ExecuteSqlInterpolatedAsync` (EF Core parameterizes `FormattableString` interpolation holes automatically; confirmed pattern at `D:\GMS\GMS\GMS.Infrastructure\Jobs\AnalyticsAggregationJob.cs:55-93`, `D:\GMS\GMS\GMS.Application\Services\PromoService.cs:114`, `CheckinService.cs:600`, `MembershipService.cs:574`, `StockTransferService.cs:388`, `SessionBookingService.cs:281,286`, `PurchaseOrderService.cs:478`, `InvoiceService.cs:466`, `PlatformBillingServices.cs:256`). The one `ExecuteSqlRawAsync` call outside test code, `D:\GMS\GMS\GMS.Platform\Persistence\MigrationImportBaselineExtensions.cs:78`, is part of the EF migration-history bootstrap tooling (not reachable via any HTTP request path) — listed here only for completeness, not as a risk.

5. **No default/seeded admin credentials found in Production config.** `PlatformSeed:Password` and `PlatformSeed:Email` are empty in `appsettings.json:26-30`, `appsettings.Production.json:34-38`; the only place a plaintext password appears is the **Development** seeder (`D:\GMS\GMS\GMS.Infrastructure\Persistence\DataSeeder.cs:63-66, 158`, `"Test@1234"` for `owner@gymflow.test` / `manager@gymflow.test` / `trainer@gymflow.test` / `receptionist@gymflow.test`), which only runs `if (app.Environment.IsDevelopment())` (`D:\GMS\GMS\GMS.Api\Program.cs:281-308`). **Not a Production risk as configured**, but flagged because (a) it's a real password string committed to source control (low sensitivity since it's dev-only and gates behind `IsDevelopment()`), and (b) for the offline "Local Lifetime Edition," if that product ever ships with `ASPNETCORE_ENVIRONMENT=Development` by mistake (e.g., an installer that doesn't set the env var), this seeding path — and its hardcoded password — would activate in a real customer's environment. Verify the offline-edition installer explicitly pins `ASPNETCORE_ENVIRONMENT=Production` (or a new dedicated environment name) and that `DataSeeder.SeedAsync()` (as opposed to `EnsureIdentityRolesAsync()`, which intentionally runs in all environments) is never reachable outside `IsDevelopment()`.

## Summary for the Local Lifetime Edition feasibility study
- The **tenant-isolation architecture (centralized EF Core global query filters, §3.2)** is a genuine strength and, if anything, *simplifies* the offline single-gym port: a single-tenant build could keep the same `TenantId` column/filter machinery with one fixed tenant row, or strip it — either way, the isolation logic is centralized in one file (`GymFlowProDbContext.cs`) rather than scattered.
- The **hard external dependency to re-architect for offline use is OTP-over-SMTP** (§1.5, P2 finding #5) — the codebase already has an internet-independent alternative (staff/HR-issued activation codes) that should become the primary/only member and employee sign-in path offline.
- The **Platform plane** (subscription billing, suspension gating via `ISubscriptionAccessService`, `TenantMiddleware.cs:113-141`) is SaaS-specific machinery that would need to be disabled or stubbed out entirely for a single-gym offline product — it's cleanly separated (own JWT audience, own DbContext/schema per `GMS.Platform`), which should make excising it comparatively low-risk.
- Two items should be resolved **before**, not after, any offline packaging work begins, since they're general hardening gaps independent of the online/offline question: the missing login rate limit (P1 #1) and the permissive Production CORS fallback (P1 #2) — neither is specific to multi-tenancy and both are worth fixing regardless of which edition ships.
