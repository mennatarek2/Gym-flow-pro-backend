# External Dependencies, Configuration, Storage & Build/Deploy Audit

Scope: `D:\GMS\GMS` (.NET backend: GMS.Api, GMS.Application, GMS.Core, GMS.Infrastructure, GMS.Platform) and `D:\GMS\GMS\Frontend` (Node/Express `apps/web`, Vite/React `apps/admin` and `apps/platform-console`, `packages/i18n`). Read-only audit for the "Local Lifetime Edition" (single Windows machine, offline) feasibility study. All findings are cited with file paths. Secret-looking values are redacted as `REDACTED`; none were found actually committed with real-looking values — all secret fields in tracked config files are empty strings.

Read the implementation of every service found (not just the grep hit) to determine whether it's a live call, a mock, or a comment/doc reference.

## 4. File Storage Audit

**Uploaded/generated file types found:** HR employee documents (`GMS.Api\Controllers\HrEmployeeDocumentsController.cs`), invoice PDFs (`GMS.Application\Services\RenderAndDeliverInvoiceJob.cs`), Z-Report PDFs (`GMS.Infrastructure\Services\ZReportPdfRenderer.cs`), tenant logos (referenced via `tenant.LogoUrl` in `RenderAndDeliverInvoiceJob.cs:70`), and generic uploads via `AdminController.cs`, `TenantSettingsController.cs`, `InventoryCatalogController.cs`, `ImportsController.cs` (all found via `IFormFile` grep).

**Storage mechanism:** All file storage flows through a single abstraction, `IFileStorageService`, implemented by `GMS.Infrastructure\Services\LocalFileStorageService.cs` — the **only** implementation registered in DI (`InfrastructureServiceExtensions.cs:147`, commented "File storage (local for dev)"). There is no cloud storage SDK (no Azure Blob Storage, no AWS S3 client) anywhere in the backend.

- **Path handling:** `LocalFileStorageService.UploadAsync` writes to `Path.Combine(_env.WebRootPath ?? ContentRootPath\wwwroot, "uploads", folder)` (`LocalFileStorageService.cs:25`) — i.e. relative to the app's own `wwwroot`, resolved to an absolute path at runtime via `IWebHostEnvironment`. Returned URLs are **relative** (`/uploads/{folder}/{uniqueName}`, `LocalFileStorageService.cs:36`), stored as plain strings in the database (e.g., `Invoice.PdfUrl`, confirmed via `RenderAndDeliverInvoiceJob.cs:77-79`).
- **Path traversal guard:** `ResolveLocalPath` rejects `..` segments and anything outside `/uploads/` or outside the resolved `uploadsRoot`, and does a `Path.GetFullPath` containment check (`LocalFileStorageService.cs:71-83`) — a reasonable safeguard for local disk storage.
- **No BLOB-in-database pattern found** for these documents — files live on disk, only the relative URL/path string is persisted in SQL. (A full sweep of every entity for `byte[]`/`varbinary` columns was not exhaustively performed beyond the invoice/PDF pipeline; if other subsystems store binary blobs in SQL, that is `UNKNOWN — REQUIRES VERIFICATION`.)
- **Publish-time exclusion:** `GMS.Api\GMS.Api.csproj` explicitly excludes `wwwroot\uploads\**\*` from publish output ("Do not deploy local dev uploads... to MonsterASP") — confirming uploads are treated as local, environment-specific, non-versioned data, consistent with a design that already assumes per-machine local storage.
- **Cloud dependency assessment:** This subsystem would work **unmodified** with purely local disk storage in an offline edition — it already *is* local disk storage; there is no code change required, only ensuring the `wwwroot/uploads` directory persists across app updates/reinstalls (a packaging/installer concern, not a code dependency).

## Summary of Findings Most Relevant to Offline Feasibility

- **No hard cloud SDK dependencies** exist in either repo (no AWS/Azure/GCP/Firebase Admin SDKs referenced in any `.csproj` or `package.json`). All "cloud" integrations (Paymob, Fawry, 4jawaly WhatsApp) are plain `HttpClient` calls to hardcoded HTTPS base URLs, and every one of them already has an existing empty-config-key fallback path (mock/no-op/error) rather than crashing the app.
- **Redis, Hangfire, and file storage are already local-first**: Redis is optional and off by default (falls back to in-memory cache); Hangfire persists to the same SQL Server database as the app (no separate cloud queue); uploaded/generated files (HR docs, invoice PDFs, Z-reports) are already written to local disk under `wwwroot/uploads` via a single `LocalFileStorageService` abstraction with no cloud storage alternative even present in code.
- **The one real, always-on external dependency for the UI is CDN-hosted assets** — Google Fonts and jsDelivr (Tabler Icons webfont, Chart.js) are loaded directly from the internet by nearly every `apps/web` HTML page and would need to be vendored locally for a genuinely offline UI experience.
- **SMTP (email OTP) is the only "real" outbound network dependency in the OTP/notification flow that isn't already mocked** — it's generic MailKit/SMTP, not a cloud SDK, so it can point at any local/LAN SMTP relay without code changes; SMS OTP and push notifications are already mock-only in code today.
- **MonsterASP-specific deployment artifacts** (publish script, `.pubxml` profiles, `monsterasp.env.example`) are cleanly separable — they configure *how to ship to that specific host*, not *how the app runs*, and would simply be unused (not reworked) for a local installer.
- **Database migrations are not automatic in local dev today** (`ApplyMigrationsOnStartup` defaults false; local scripts run `dotnet ef database update` explicitly) — a local installer would need to decide whether to flip this default to `true` for a zero-touch first-run experience, mirroring what's already done for the MonsterASP Production config.
